# Workbench Agent Acceptance Checks

Status: frozen before implementation
Started: 2026-08-06 06:51 ET
Target: the shared `ipcorp-brain-frontend` checkout
Scope extension recorded: 2026-08-06, after the Fabric Toolbox comparison

## User outcome

A new Workbench user can ask for help from any page, get an answer based on the
current Workbench and its connected services, move directly to the right page and
section, and ask the agent to carry out an available UI action. Maintenance work is
kept inside the same experience, with an explicit review step for anything that
changes data, files, or an external service.

## Required behavior

1. The agent is mounted once at the application shell, stays available on every
   Workbench page, works at desktop and phone widths, and can be minimized without
   losing the current conversation.
2. Responses use the Claude Agent SDK with the local Claude Max OAuth session.
   Text and reasoning status stream as they happen. A visible Stop control cancels
   the active request. Fake waits and canned completion text are not acceptable.
3. Every answer distinguishes current evidence, connected-service results, and an
   unavailable source. The UI never presents an unavailable connector as a successful
   lookup and never exposes credentials, cookies, internal prompts, or raw tool output.
4. Navigation covers every current `ViewKey`. A destination can include a registered
   section. The client changes the Workbench view, waits for the view to render,
   scrolls the section into view, focuses it, and announces the result.
5. The client supplies a fresh semantic list of currently available controls with
   each request. The service may use only an action key from that list. Page changes,
   focus, disclosure, and scrolling can run immediately. Form filling may run with a
   visible notice. Submit, delete, send, apply, save, external update, and file change
   actions require a review card and explicit confirmation.
6. The service supports current Workbench data, Team Library files, live Jira reads,
   and direct Microsoft 365 MCP reads. Jira changes and Microsoft 365 changes remain
   impossible until the exact proposed action is confirmed.
7. NotebookLM status, notebook listing, and artifact listing are read actions.
   Generation and download require confirmation and always use an explicit notebook
   ID. A generation request returns its task or artifact ID without holding the chat
   open through a long polling loop.
8. DevSpace access is limited to the exact frontend checkout. Read, search, and an
   allowlisted verification command can run automatically. Edit, write, and any other
   command require confirmation, a visible file or command preview, and a receipt.
   Arbitrary filesystem paths and arbitrary shell text are rejected.
9. A same-origin local owner session is established with an HttpOnly cookie and an
   in-memory request token. Confirmations are tied to that session, expire, are
   single-use, and validate the original tool name, arguments, and target again.
10. The service binds to loopback, accepts only the configured Workbench origins, and
    rejects forged action keys, expired confirmations, replay, malformed inputs,
    unregistered destinations, and requests for resources outside the selected repo.
11. The widget includes clear connection and maintenance readiness, source receipts,
    useful empty and error states, keyboard operation, screen-reader labels, focus
    management, reduced-motion behavior, and no overlap with the mobile tab bar.
12. Existing Workbench routes, Jira work, meeting work, and local uncommitted changes
    remain intact.
13. The local owner Workbench can run bounded, read-only SQL against the five approved
    IP Corp data sources, inspect Power BI semantic models, run read-only DAX, and read
    Fabric workspaces, lakehouses, schemas, jobs, schedules, compute, connections,
    lineage, and capacities. SQL comments, batches, writes, SELECT INTO, and unbounded
    detail reads are rejected before an MCP call.
14. Power BI model changes and Fabric cache administration always produce one exact
    review card first. The review names the tool, operation, arguments, target, and risk;
    confirmation is single-use. Enterprise data tools are unavailable from a public
    Workbench session until an owner identity check is added there.
15. The chat keeps a compact source and tool activity trail, renders tables and code in
    responses, and lets the user copy an answer without exposing raw credentials or
    unfiltered MCP responses.

## Verification evidence required

- Focused unit tests for destination lookup, semantic action validation, permission
  classification, session ownership, confirmation expiry and replay, path checks, and
  connector result sanitizing.
- Gateway tests proving allowed reads and denied forged, cross-origin, expired,
  replayed, and out-of-repo requests.
- TypeScript, production build, and focused Biome checks for every touched file.
- Browser checks for global presence, real streaming states, Stop, page plus section
  navigation, current-page UI action, review and confirm, connector-unavailable state,
  source activity, rich result formatting, keyboard use, and phone layout.
- Unit checks for SQL read validation, SQL source routing, Power BI read versus reviewed
  change classification, Fabric read versus reviewed administration, and result
  sanitizing.
- The real `C:\Apps\IP Corp Brain Launch.bat` path, direct UI health on port 5217,
  direct service health on port 8817, one safe live Workbench lookup, and one safe live
  connected-service read.
- Fresh review of the final diff and evidence before completion is reported.
